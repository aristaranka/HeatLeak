## When `npm run build` itself won't run in your shell

A host app's `vite.config.mts` commonly requires platform-injected env vars
(e.g. `VITE_C3_PKG`, `VITE_C3_ENV`, `VITE_C3_APP`) that a managed dev/build
service sets automatically but a plain interactive shell does not. Failing with
`VITE_C3_PKG is not set` (or similar) from a raw shell invocation is an
environment gap, not a wiring bug — don't invent or guess values for these vars.
For partial signal without them, run the type-check and lint steps directly (e.g.
`npx eslint --ext .js,.ts,.tsx src --quiet` and `npx tsc -p tsconfig.build.json`),
and treat the managed dev server's own logs as the authoritative build/runtime
check once those platform vars are available.

One exception is worth knowing: in a **C3 Code** consumer, `VITE_C3_PKG` is not a
guess — it is the package name, exported as `$MAIN_PKG_NAME` in the agent shell —
and this template's **build** path reads no other `VITE_C3_*` var
(`VITE_C3_ENV`/`VITE_C3_APP` shape only the dev-serve base). So
`VITE_C3_PKG=$MAIN_PKG_NAME npm run build` produces the real bundle, which
upgrades the verify ladder: run `scripts/verify_embed.sh` (or the CSS grep
directly) against the emitted `ui/content/<pkg>/assets/*.css` instead of stopping
at lint + type-check.
