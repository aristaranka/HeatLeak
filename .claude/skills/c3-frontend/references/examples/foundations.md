# C3 Design System foundations

Conventions for coding agents using `references/examples/`. Read this before inventing
props, colors, typography, or page chrome.

Page-level theme utilities for C3 Code packages live in `references/styles.md`. This file
covers the shared component contract used by the cards and sources under `examples/`.

## Component API (two-axis model)

Most design-system components share one vocabulary:

- **`variant`** — how the surface is drawn: `solid`, `soft`, `outline`, `ghost`
- **`appearance`** — semantic meaning: `accent`, `success`, `warning`, `danger`, `info`, …
- **`size`** — `sm`, `md`, `lg`

The prop name is always `appearance`. Never `tone`, `color`, or `theme` for that axis.

## Dark mode

Token values swap when the document root has the **`.dark`** class. Components must not
write `dark:` Tailwind variants or separate dark stylesheets; they flip when tokens flip.

Prefer toggling `.dark` on `<html>` to match the CSS that ships with these examples.

## Colors

- Prefer semantic roles / tokens, never raw hex or palette utilities (`bg-blue-600`).
- In these components: `bg-[var(--c3-style-basic-…)]`, `text-[var(--c3-style-basic-…)]`, etc.
- Decorative / chart scales (`--c3-style-deco-*`, `--c3-style-chart-*`) only when a semantic role does not fit.
- Never hardcode hex or add per-component `dark:` forks.

## Typography

When styling these design-system components, prefer the text utilities they already use:

- Pattern: `text-c3-{regular|bold}-{display|heading|body|label|code}-*`
- Examples: `text-c3-bold-heading-h4`, `text-c3-regular-body-p2`
- The class carries size + line-height; do not restyle those separately.

For ordinary page copy on a template that already follows `references/styles.md`, keep using
that file's type classes (`text-2xl font-medium text-primary`, …).

## Icons

- Library: **Lucide** (`lucide-react`) only.
- Pass icons into slots (`leadingIcon`, `icon`, …); do not invent an icon registry.
- Size with `size-*` (slots often default to `size-4`). Color via `currentColor` / parent text color.

```tsx
import { Search } from 'lucide-react'

<Button leadingIcon={<Search />}>Search</Button>
```

## Styling contract

1. Tailwind + `cva` + `cn()` in the `.tsx` is primary.
2. Classes resolve to C3 tokens; SCSS is last resort (complex keyframes only).
3. States: `hover:` / `active:` / `focus-visible:` / `disabled:` / `data-[state=*]:`.
4. Components may emit `data-variant` / `data-appearance` / `data-size` for selectors; style via `cva`, not those attributes alone.

## Page chrome and layouts

- Shell: `page-layouts/_shell/AppShell.tsx` (prefer SideNavPanelV2 / `navVariant="v2"` when available).
- Page shapes: `page-layouts/ListPage`, `DetailPage`, `DashboardPage`, plus `EmptyState` / `LoginPage`.
- `PageHeader` is typically flush with the chrome; put content padding (`p-6`) on the body below the header, not around the header itself.

## Vendoring into a workspace

1. Open `index.md` → matching `*.md` card for import + JSX + props.
2. If `src/components/ui/<name>` is missing, copy from `ui/`. If `src/lib/utils.ts` is missing, copy `helpers/utils.ts` → `src/lib/utils.ts`.
3. If styles look wrong after copying `ui/`, copy / merge `styles/` (see `styles/README.md`).
4. For a full page, start from `page-layouts/` instead of assembling chrome from scratch.
5. Install runtime deps the source imports: `radix-ui`, `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react`, and feature libs as needed (`react-day-picker`, …).
